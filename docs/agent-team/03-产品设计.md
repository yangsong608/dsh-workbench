# 智能体团队 · 产品设计

> 版本：v1（2026-10-23） · 依赖：`01-需求与技术分析.md`、`02-可行性评估.md`
> 一句话：**团队是"配置"，会话是"运行"，记忆是"资产"**——三者同库、同一套 UI 语言。

---

## 1. 设计原则

1. **不造第二个 Agent 运行时**：执行一律是 DSH 会话；工作台只做配置、派发、呈现。
2. **模板态 ≠ 运行态**：门户里的团队是模板（不会后台空转）；只有派发后才有"运行中"。
3. **事件驱动，不轮询**：会话消息、成员状态、任务变化都来自事件/投影。
4. **失败可见**：每一层（成员/任务/派发）都有明确状态与原因，不吞错。
5. **记忆可审计**：每条注入的记忆/知识都能看到来源、作用域、时间，可删除。

## 3. 默认团队：产品研发

| 成员 | 角色 | 默认职责 | 默认工具 | 记忆 |
|---|---|---|---|---|
| 主理人 | lead | 拆任务、派成员、验收、汇总 | 全部 + 团队工具 | 团队 + 项目 |
| 产品 | product | 用户/场景/价值/边界 | 检索、文件读 | 团队 + 项目 |
| 架构 | architect | 技术方案/风险/取舍 | 检索、文件读、代码读 | 团队 + 项目 |
| 前端 | frontend | 交互/组件/样式 | 读写代码、检索 | 团队 + 项目 |
| 后端 | backend | 接口/数据/任务 | 读写代码、检索 | 团队 + 项目 |
| 测试 | qa | 用例/边界/回归 | 读、测试运行 | 团队 + 项目 |
| 评审 | reviewer | 独立复核、挑错 | 只读 | 团队 + 项目 |

**默认 7 人全部启用（已定）**。7 人意味着最多 7 份模型调用，成本与延迟都高于 5 人；因此配套三条约束：

- **团队同时在跑成员数默认 3**（软约束：由 kickoff 要求 Lead 同时只 assign 3 个 in-progress 任务；DSH 本身没有团队并发阀）；
- 任务按 DAG 串行/分层，不追求全员同时开工；
- 单次派发预算默认 15 分钟 / token 上限（超出即 `timeout`，保留部分结果）。

> 注意区分：成员字段 `concurrency`（默认 1）是"该成员同时接几个任务"，与团队级"同时在跑几个成员"（默认 3）不是一回事。

如后续觉得慢，可在团队详情里一键停用"后端/评审"，不影响已有配置。

**成员字段**

| 字段 | 说明 |
|---|---|
| name | **团内**唯一、≤12 字，创建后不可改（DSH 约束） |
| role | lead / product / architect / frontend / backend / qa / reviewer / custom |
| intro | 一句话职责（进系统提示） |
| systemPrompt | 追加指令（≤4000 字） |
| model | 可选，覆盖默认模型 |
| tools | 工具白名单（默认按角色预设） |
| skills | 绑定的 skill 名称列表 |
| mcp | 绑定的 MCP server 列表 |
| memoryScope | none / personal / project / team / all |
| concurrency | 该成员同时任务数（默认 1） |
| fileWrite | 文件写权限：`read` / `write`；角色预设，可改（见 3.1） |

### 3.1 文件权限：默认按角色，运行时可改（已定）

| 角色 | 默认 fileWrite | 理由 |
|---|---|---|
| 主理人 | read | 只调度与汇总，不直接改文件 |
| 产品 | read | 产出为文字与节点 |
| 架构 | read | 方案与风险，不改实现 |
| 前端 / 后端 | **write** | 实现类工作，需要写文件 |
| 测试 | read | 只读验证与运行命令 |
| 评审 | read | 独立复核，不允许顺手改 |

**"运行时可改"的准确含义**（受 DSH 约束）：

- 在团队详情或派发面板切换成员权限 → **对下一次派发生效**（推荐，零副作用）；
- 对**正在运行**的成员：DSH 的工具策略在成员创建后**不可变更**，且 teammate **名字不可复用**，因此不能"原地重建同名成员"。若要立即生效只有一条路：按新配置创建一个**替代成员**（如 `backend-2`），由 Lead 重新分配任务、`interrupt_agent` 旧成员；UI 明确提示"将创建替代成员，旧成员结果保留"；
- 所有成员都可以调用 `workbench_idea_expand` 写灵感节点——这是**结构化写入**，不是文件写工具，不受 `fileWrite` 限制。

**执行方式**：成员创建时按 `fileWrite` 生成工具策略（read 成员的工具白名单排除写类工具，如 `write` / `edit`；write 成员保留；`workbench_idea_expand` 属于结构化节点写入，read 成员也保留），并在 kickoff 中再次声明；DSH 审批作为第二道闸。**依赖条件**：实验版 `spawn_teammate` 没有 toolPolicy 字段，需要用 `@nanmicoder/dsh-agent-teams` 的 `agent_teams_add_member(tool_policy)`（见 02 S8）；若两个都不满足，则退化为 kickoff 软约束 + 审批 + 事后审计，并在 UI 标注"软约束"。**运行中不可热改**——这是 DSH 的硬约束，不是本设计的取舍。

## 4. 自定义智能体

- 入口：门户团队卡片「＋ 新建智能体」、团队详情「成员」页；
- 表单：名称、角色（预设 + 自定义）、职责、系统提示、模型、工具、技能、MCP、记忆范围；

- 模板：提供"研究员 / 文案 / 数据分析 / 法务 / 运维"等预设，一键创建再改；
- 归属：可加入现有团队（多选）或新建团队。

## 5. 页内会话

### 5.1 布局

**已定：默认右侧抽屉**。

- 灵感页「画布 + 右侧 360px 会话抽屉」，宽度可拖 320–560，记忆上次宽度；
- 窄屏（<1100px）自动改为底部 45% 分栏（响应式兜底，不作为默认）；
- 关闭抽屉不终止会话（后台继续），顶部保留状态条可重新展开；
- 抽屉与画布可同时操作：拖节点、看消息互不打断。

### 5.2 消息类型

| 类型 | 渲染 |
|---|---|
| 主理人消息 | 头像 + 「主理人」徽章 + Markdown |
| 成员消息 | 成员名 + 角色色 + 缩进分组（同一成员连续消息合并） |
| 工具调用 | 单行折叠：`▸ 工具名 参数摘要`，可展开看结果摘要 |
| 任务卡 | 任务 id + 标题 + 状态（pending/running/done/failed） |
| 成员状态 | `产品 已加入 / 测试 超时（重派中）` |
| 系统 | 派发开始、完成、失败、超时、取消（带原因与操作按钮） |

> v1 用轻量 Markdown（标题/列表/代码块/链接/行内代码），自己实现 ~100 行渲染器，不引第三方库，也不依赖 DSH 官方消息组件。

### 5.3 控制

UI 上的控制动作只有两种实现路径，设计里必须写清，避免"按钮点了没反应"：

| 动作 | 路径 A（MVP，提示词驱动） | 路径 B（1.10，host 直连） |
|---|---|---|
| 停止成员 | 向 Lead 发一条 `interrupt <name>` 指令 | `ctx.agentTeams.interrupt(leadAgent, name)` |
| 停止整体 | 发 `stop` 指令 + 结束会话 | 关闭会话 + 中断所有成员 |
| 重试失败任务 | 发 `retry <taskId>` 指令 | `ctx.agentTeams.updateTask(...)` 重开任务 |
| 追加指令 | 输入框 → `sessions.prompt`（steer 语义） | 同左 |
| 改成员权限 | 下一次派发生效 | 创建替代成员（新名字）+ 中断旧成员 |
| 打开完整会话 | `uiWorkspace.openSession(sessionId)` | 同左 |

> 路径 B 依赖实验 API 与实时 `Agent` 句柄，作为 1.10 的增强；MVP 全部走路径 A，并在 UI 上标注"由主理人执行"。

### 5.4 空态与首次派发

未派发时抽屉显示：团队选择器 + 任务说明输入 + 「开始发散」；点开始 = 创建会话 + 发 kickoff + 抽屉切换为运行态。

## 6. 派发协议（kickoff 契约）

派发时发送一条结构化提示词（不是自由聊天）：

```
你是「{teamName}」的主理人。目标：{goal}
工作区：{workspacePath}
输入：{idea title/brief/inputs 摘要}
可用工具：workbench_idea_expand（写节点，支持 final）、workbench_idea_progress
约束：
1. 先在任务板建任务（每个方向/模块一条），再按成员职责创建 teammate（最多 {n} 个）；
2. 成员完成后必须调用 workbench_idea_expand 写入节点，parentId 用返回的 id；
3. 全部完成后调用 workbench_idea_progress(done)，并给出一句话总结；
4. 成员失败/超时要重派一次，仍失败就在总结里说明，不要静默跳过；
5. 不要修改工作区里与本任务无关的文件。
```

**状态机**

```
idle → dispatching → running → (done | done(partial) | failed | timeout | cancelled)
                       ↑  │
                       └──┴─ 重试（只重派失败任务）
```

- `dispatching`：会话创建/首条消息发送中（≤30s）；
- `running`：收到会话事件；同时展示成员 x/y、任务 n/m；
- `done`：`workbench_idea_progress(done)` 或 Lead 输出完成总结；
- `failed`：会话错误/团队成员全部失败；
- `timeout`：超过派发预算（默认 15 分钟，可在设置里改）；
- `cancelled`：用户停止。

### 异常处理矩阵

| 场景 | 检测 | 行为 |
|---|---|---|
| 成员创建失败 | roster `failed` | 提示并允许换成员重试 |
| 成员超时 | 单任务无事件 > 5 分钟 | Lead 重派；3 次后标 failed |
| 工具调用失败 | 工具结果 error | 展示错误、保留已写节点 |
| 会话崩溃 | session 状态 error | 标记 failed，可一键重试（新会话） |
| 整体超时 | dispatch 超预算 | 停止、保留部分结果、可续跑 |
| 部分成功 | 版本已生成但成员未全完成 | 标 `done(partial)`，列出缺失方向 |

## 7. 记忆与知识系统

### 7.1 记忆分层

| 层 | 存储位置 | 谁写 | 谁读 |
|---|---|---|---|
| 个人 | `<DSH_HOME>/dsh-workbench/memory/*.md` + 索引（默认 `~/.dsh/...`） | 用户、主理人（明确指令） | 所有团队（**成员默认不读个人记忆**，需显式开启） |
| 项目 | `<workspace>/.dsh-workbench/memory.md` | 成员/主理人 | 该项目所有团队 |
| 团队 | SQLite `agent_memory`（scope=team） | 主理人 | 该团队成员 |
| 会话 | DSH session 日志 | 自动 | 仅本会话 |

写入规则（已定：**手动确认**）：

- 会话结束给"建议记忆"卡片（3–5 条），用户逐条采纳才写入；
- v1 **不提供自动写入**；自动提取列为 v2 候选，前提是先有"误写回滚 + 批量撤销"机制；
- 采纳时可选作用域（个人 / 项目 / 团队），默认取团队模板的 `memoryScope`。

### 7.2 知识系统

- 索引范围：**按项目隔离**的工作区文本文件（md/txt/代码/文档解析）、笔记、灵感图、Bug/测试记录；跨项目不互相注入；
- 分块：按标题/段落，512–800 字，带路径与行号；
- 检索：FTS5 BM25 + 类型/路径过滤；返回 top-k（默认 6）——本机已实测 Node 24 的 `node:sqlite` 支持 FTS5（SQLite 3.53.4）；
- 注入：派发时检索一次，拼进 `<knowledge>`；
- 工具：`workbench_knowledge_search(query, scope?, topK?)`；
- UI：团队详情「知识」页可看索引状态、最近索引、检索测试；会话里显示"本次注入 6 条"可展开。

### 7.3 记忆/知识注入格式

```
<memory scope="project" updated="2026-10-20">
- 交付证据审查：报告口径必须与 PPT 一致，禁止自造百分比
</memory>
<knowledge>
[1] path: 交付/评审表.md#L12-L40 · score 0.82
...
</knowledge>
```

## 8. 数据模型

| 表 | 关键字段 |
|---|---|
| `agent_teams` | id, name, desc, is_default, default_workspace, created_at |

| `agent_dispatch_members` | dispatch_id, member_id, member_name, session_member_name, file_write, status, error, joined_at（**记录每次派发的成员快照与权限**） |

| `knowledge_chunks` | id, doc_id, ord, text, tokens |

## 10. 权限与安全

- 工具白名单按成员配置（与 `fileWrite` 联动，见 3.1）；高风险写操作用 DSH 审批；
- 文件写权限默认：前端/后端可写、其余只读；**运行中不可热改**——只对下一次派发生效，或创建替代成员（新名字）；
- 记忆默认只在本机；项目记忆进仓库前需用户勾选；
- 知识注入带来源，不执行知识里的指令（防提示注入）；
- 团队派发互斥：同一灵感同时只能有一个运行中的 dispatch；
- 成本护栏：默认 7 成员、**团队并发 3（软约束，靠 kickoff 与任务板 owner 数）**、单次派发 token 预算、15 分钟超时（工作台计时，DSH 无内建任务超时）。

## 12. 验收标准

**1.8 验收（1–8）**

1. 门户功能区下方显示「智能体团队」，默认「产品研发」含 7 名成员，成员卡片可点开详情；
2. 新建自定义智能体后，能加入团队并在派发时被创建为 teammate；
3. 灵感点「生成」在右侧弹出会话抽屉（320–560 可拖），30 秒内出现主理人消息与成员状态；
4. 会话期间成员/任务视图实时更新，能停止、能重试失败任务；
5. 完成时灵感图新增 ≥6 个节点并生成版本，会话显示完成总结；
6. 模拟成员失败与整体超时，UI 分别显示失败/超时并保留部分结果；

**1.9 验收（9–11）**

9. 会话结束弹出「建议记忆」卡片，未采纳的记忆不会出现在下次派发注入中；
10. 记忆注入可在会话中查看来源，删除后不再注入；
11. 知识检索对工作区文档返回相关片段（top-3 命中率人工抽检 ≥80%）。
