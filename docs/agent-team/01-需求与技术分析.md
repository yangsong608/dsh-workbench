# 智能体团队 · 需求与技术分析

> 版本：v1（2026-10-23） · 范围：个人工作台「智能体团队 + 页内会话」需求
> 分析对象：PixOffice、WorkBuddy（本机 4.x 桌面端）、DeepSeek Harness（本仓库 dsh-v0.2.1-rc.2 源码）

---

## 0. 需求拆解

| # | 原始需求 | 拆成可实现的系统能力 |
|---|---|---|
| 1 | 分析 PixOffice / WorkBuddy 的智能体团队原理（调度/执行/反馈、异常/失败/超时） | 调研 + 对照，输出可直接借鉴的机制清单 |
| 2 | 门户功能区下方增加「智能体团队及其成员」，默认「产品研发整个团队」，支持自定义新智能体 | 团队注册表 + 成员配置 + 门户区块 + 自定义表单 |
| 3 | 分析 DSH AI Agent 原理（模型/MCP/skills/RAG/提示词） | 技术底座分析，确定集成面 |
| 4 | 智能体使用 DSH 的 AI Agent | 团队会话由 `ctx.sessions` / `ctx.agents` 驱动，不另造 agent 运行时 |
| 5 | 灵感 AI 发散时页内弹会话框，使用灵感配置的智能体，由团队负责人调度执行 | 页内会话组件 + 派发协议 + 成员/任务实时视图 |
| 6 | 团队/成员支持项目记忆、个人记忆、知识系统 | 记忆分层 + 知识索引 + 检索注入 + 作用域隔离 |

**关键判断**：需求 2/5/6 不是三个孤立功能，而是同一套「团队运行时 + 会话界面 + 记忆」的三种视图。设计必须共用一套数据模型，否则会出现"门户里配的团队、灵感里用不到"的割裂。

## 1. PixOffice 的工作原理

### 1.1 它是什么（先纠正一个常见误解）

PixOffice（[workbzw/pixoffice](https://github.com/workbzw/pixoffice)，MIT，TypeScript）**不是智能体编排器**，而是一个 **2D 办公室可视化 + 消息转发服务**：

- 前端：Vite + React + PixiJS，渲染人物/工位/白板/会议室；
- 服务端：Fastify，缓存"最新业务状态"并通过 SSE 推给浏览器；
- 业务方：**外部后端**（也就是真正跑 agent 的系统）负责调度、执行与状态计算，PixOffice 只负责展示与转发。

官方接入文档写得很明确：外部业务后端"提供办公室、成员、任务和白板数据，**执行业务操作**，调用 PixOffice HTTP 接口"；PixOffice 服务端"校验请求、缓存最新业务状态，并将消息发送给浏览器"。

所以：**调度/执行在 PixOffice 之外**，PixOffice 提供的是「控制面 → 表现面」的协议。这一点决定了我们不能"照抄 PixOffice 做调度"，只能借鉴它的**协议语义与异常模型**。

### 1.2 协议与生命周期

| 动作 | 方向 | 语义 |
|---|---|---|
| `office.capabilities` | 业务 → PixOffice | 查询可用的能力/实体，用于动态适配 |
| `offices.initialize` | 业务 → PixOffice | 提交办公室、成员、可选聊天地址；浏览器回 `reply` 确认 |
| `office.snapshot` | 业务 → PixOffice | 全量快照 + 递增 `seq`，服务端做版本校验后缓存并 SSE 下发 |
| `scene commands` | 业务 → PixOffice → 浏览器 | `teamId + command`，浏览器本地排队、寻路、播放动画；**200 只代表已转发** |
| `ui.next` / `ui.respond` | 业务 ↔ PixOffice | 用户点击被"领取"：业务方持续领取，处理后回填 |
| `decision.request` | 业务 → PixOffice | 限时选择菜单；超时返回 408 并关闭菜单 |
| `chat`（history/send/resume/cancel） | 浏览器 ↔ 业务聊天服务 | PixOffice 只做转发与校验，历史与生成状态由外部聊天服务保存 |

### 1.3 异常/失败/超时的处理（最值得借鉴的部分）

| 状态码 | 含义 | 对我们的启示 |
|---|---|---|
| `200` | 已处理/已转发成功 | **"已接收"必须与"已完成"分开表达** |
| `202` | 最新状态已缓存，但未取得浏览器应用确认（页面离线或确认队列满） | 异步投递要有"已入队未确认"态 |
| `408` | 等待浏览器处理或用户选择超时 | 超时是**协议内的一等状态**，不是异常 |
| `409` | 版本冲突 / 菜单 ID 冲突 / 没有在线接收者 | 状态机冲突要能识别并重试 |
| `410` | 用户操作已结束或超时 | 幂等键过期语义 |
| `413` | 快照超限 | 输入上限前置校验 |
| `422` | 浏览器处理业务数据失败 | 前端执行失败要回流给业务方 |
| `503` | 队列/缓存/连接/发送缓冲达到上限 | 背压要显式 |

其它关键事实：
- 服务端重启后**必须重新初始化**（内存态，无持久化）；
- SSE 重连只补最新快照，不补事件流；
- 官方明确"不提供网络重试的业务去重保证或已结束结果查询"——**幂等由业务侧自己负责**。

### 1.4 可借鉴 / 不可借鉴

**借鉴**：三层分离（编排/执行 vs 表现 vs 存储）、快照 seq + 版本校验、`202/408/409/410` 语义、命令幂等键、UI 操作领取模型、能力发现。

**不借鉴**：它的可视化与"办公室"交互；它不是调度器，硬套会得到一套"好看但不管用"的壳。

## 2. WorkBuddy 的工作原理

### 2.1 它是什么

腾讯 WorkBuddy 是一款桌面 AI 工作台（Electron，本机 `/Applications/WorkBuddy.app`）。本机还装了 `dsh-connect-workbuddy` 5.4.0，但它**只是模型接入**（把 WorkBuddy 登录态包装成 DSH 的模型 provider / 积分徽章），与"智能体团队"无关——团队是 App 自己的会话能力。

以下结论来自本机 `app.asar` 渲染层的可读符号与文案（逆向观察，仅供设计参考，不代表官方实现细节）。

### 2.2 团队模型（从代码符号还原）

| 概念 | 证据 | 含义 |
|---|---|---|
| AgentTeam | `teamByName`、`getAgentTeams()`、`getDeletedTeamNames()`、`AgentTeamChanged` | 团队是**会话级**对象，挂在某次请求/会话下 |
| 主理人 | 文案 `teamLeader: 主理人` / `teamLeaderBadge: Lead` | Lead 是团队负责人 |
| 团队成员 | `teamMembers: 团队成员`、`member_status_change` | 成员有独立状态与职责 |
| 子智能体 | `subAgents`、`state === 'running'`、`canHoldRuntime()` | 成员以子 agent 形式运行，占运行时槽位 |
| 团队空闲 | `teamIdleByName`、`hasUnsettledTeamRuntime()`、`settleTeam` | **必须所有成员 + 运行时都结算，团队才算空闲** |
| 技能 | `teamSkills: 使用技能` | 团队/成员可绑定技能 |
| 权限门 | `SubAgentToolPermission`、`permissionRequestId`、`needApprove` | 子智能体的工具调用可被审批拦截 |
| 关闭开关 | `CODEBUDDY_DISABLE_AGENT_TEAMS` | 团队是可选能力，可整体关闭 |

### 2.3 调度 / 执行 / 反馈

> 以下为基于渲染层符号与文案的行为**推断**（非官方文档），用于设计参考。

- **调度**：主理人在会话中被用户派活，决定拆几个子任务、创建哪些成员；子智能体有独立上下文（可从主理人 fork 或全新开始）。
- **执行**：每个子智能体是独立 runtime + 独立工具调用序列；团队共享同一工作区/会话产物（artifact panel）。
- **反馈**：渲染层收到的是**结构化事件流**——`agentTeamChanged`、`member_status_change`、`stateChanged`、`queueUpdated`、`artifactUpdated`、`RequestUpdated`、`listChanged`；消息本身流式增量。UI 不轮询。
- **空闲判定**：`hasActiveChildAgents()`（有 running 且占运行时的子 agent）或 `hasUnsettledTeamRuntime()` 为真时，团队不空闲；`settleTeam` 把状态收敛（含 cancelled）。

### 2.4 异常 / 失败 / 超时

| 机制 | 证据 | 行为 |
|---|---|---|
| 自动化终态 | `AutomationCompleted / Failed / Cancelled / TimedOut` | 超时是**显式终态**，不是抛错 |
| 队列暂停 | `runtime.paused`、`pauseReason === 'error'`、`lastError` | 出错会暂停队列而不是丢弃 |
| 重启恢复 | `normalizeQueueForRestart` 把 `sending` 归回 `pending`、重排 order | 进程重启后不丢队列、不重复发送 |
| 迟到运行时 | `reportedLateRuntimes`、`retain-terminal-display` | 父请求结束后到达的子事件仍可展示，但不再占运行时 |
| 工具权限 | `SubAgentToolPermission` + `needApprove` | 高风险工具调用要人工批准 |
| 团队拆除 | `deletedTeamNames` | 团队删除是软删除/可追踪 |

**可借鉴**：主理人 + 成员两角色、事件驱动 UI、团队空闲的严格判定（成员 + 运行时双条件）、超时作为终态、队列暂停/恢复、权限门。

## 3. DSH AI Agent 原理

### 3.1 总体架构

DSH 是"全插件"的 Cordis 应用：能力=包，装配=profile 的 bundle 列表，插件之间只通过 `ctx` 服务与事件耦合。

一个轮次的固定链路（`docs/subsystems/core.zh.md`）：

```
agent-loop 认领排队提示词
  → ctx.sessions 开启轮次（事件溯源日志，唯一真源）
  → ctx.systemPrompt 组装请求前缀（系统提示词 + 工具 schema + 运行时上下文）
  → 从日志派生历史
  → LLM seam 流式取回模型响应（ctx.llm / provider 适配）
  → ctx.tools 分发工具调用（带作用域与执行流水线）
  → 每个模型可见事实追加回日志
  → 下一步再派生
```

**核心不变量：`session` 日志是唯一真源，模型可见 ⟺ 已记录。** 这让"页内会话回放、团队事件投影、重启恢复"都变成读日志，而不是另建状态。

### 3.2 模型 / 提示词

- **模型**：`modelSelection` 按 agent 投影（团队成员的模型可不同）；provider 由 `llm-*` 包适配（DeepSeek 官方、OpenAI 兼容、本机 WorkBuddy 网关等）。
- **提示词**：`system-prompt` 负责分段组装（身份、运行时上下文、工具说明、项目指令），`context/agent-instructions` 读取 `AGENTS.md` / `CLAUDE.md` 之类项目指令，`context/file-reference` 提供按 agent 作用域的文件引用。
- **压缩**：`compaction`（basic / command）在上下文接近上限时摘要历史，保证长会话可继续。

### 3.3 MCP

`mcp-client` 连接配置的 MCP server，把其工具、资源、指令注入到**作用域内有该 server 的调用方**；`mcp-resources` 提供显式选择 server 的资源发现/读取工具。也就是说 MCP 是"按 agent 作用域生效"的，不是全局一股脑注入——这正好支持"不同成员挂不同 MCP"。

### 3.4 Skills

`skill-filesystem` 从项目 / 自定义 / 用户目录发现 `SKILL.md` 并监视变更；`tool-skill` 把**目录**给模型，模型按需 `skill` 加载完整指令。技能是"渐进披露"的提示词资产，不占常驻上下文。

### 3.5 RAG 与记忆

DSH **没有内置向量 RAG**。上下文来源是：项目指令（AGENTS.md）、文件引用、会话历史、压缩摘要、记忆类插件（本机装了 `dsh-mnemon`，提供 Documents/Recall 语义记忆）。

所以"知识系统"必须由我们补：本项目里最合适的是工作台自己的 SQLite（FTS5 全文）+ 文件索引，可选再加 embedding。理由：本地优先、零外部依赖、与灵感/笔记/交付物天然同库。

### 3.6 子智能体与 Agent Teams（本需求的直接底座）

DSH 已内置实验性 **Agent Teams**（本机 desktop profile 已启用 `@deepseek-ai/dsh-experimental-agent-team-profile`，并有第三方 `@nanmicoder/dsh-agent-teams`）：

- **身份**：`TeamId = root SessionId`，隐式团队，不存在"创建团队"事件；Lead 是 root agent。
- **成员**：`provisioning → active | failed` 是持久态；`running / inactive` 是派生态（有轮次在跑 vs 空闲）。名字不可变、不复用。
- **消息**：直接投递到目标 inbox（running 在步骤边界 steer；inactive 冷恢复）；**没有 outbox、重启不重试、不按显式重发去重**。
- **任务板**：`TeamTaskSnapshot` 全量版本化，`revision` 做 CAS，`blockedBy` 必须是 DAG，`writeScopes` 只是提示性路径前缀（不锁）。
- **工具**：`spawn_teammate / send_message / interrupt_agent / list_agents / wait_agent / team_task_*`（本会话即可见）。
- **等待**：`waitForChange(10s–1h)` 只报告变化或超时，不搬运状态。
- **投影**：Lead 会话把 roster + 任务视图发布为 `agentTeam` 客户端投影，Web/Desktop 的 Team UI 直接渲染成员与任务板。**第三方客户端能否直接读该投影需验证（Spike S2）**；读不到只能解析工具事件降级。
- **上限**：`maxMembers 16`、`maxTasks 256`、单条消息 64KiB、disposal 5s；超限返回类型化错误。
- **限制**：共享工作目录、不支持独立工作目录/跨进程协调、不自动释放任务 owner；实验性 API 可能变动。
- **成员工具策略**：实验版 `spawn_teammate` 的请求字段只有 name/description/prompt/context/provider/cancellation，**没有 per-member toolPolicy**；本机另装的 `@nanmicoder/dsh-agent-teams` 通过 `agent_teams_add_member(tool_policy)` 支持按策略限制成员工具。工作台若要做"read 成员不能写文件"的硬约束，需要走后者或接受软约束。

**这解决了需求 4 与需求 5 的"谁来调度"**：不需要造调度器，直接让 Lead agent 用 Team 工具调度；工作台负责"配置团队 + 派发任务 + 呈现结果"。

## 4. 三家对照

| 维度 | PixOffice | WorkBuddy | DSH Agent Teams |
|---|---|---|---|
| 定位 | 2D 可视化 + 转发 | 桌面 AI 工作台（含团队） | Agent 运行时 + 团队域 |
| 谁调度 | **外部后端**（它不管） | 主理人（Lead） | Lead agent |
| 谁执行 | 外部 agent 系统 | 子智能体 runtime | teammate 子 agent |
| 反馈形态 | HTTP 响应 + SSE + reply | 结构化事件流 + 流式消息 | 会话日志 + agentTeam 投影 |
| 超时 | 408，菜单超时关闭 | `TimedOut` 自动化终态 | `waitForChange` 超时；任务无内建超时 |
| 失败 | 409/422/503 分类 | 队列暂停 + lastError | 成员 `failed`、任务 CAS 冲突、上限错误 |
| 持久化 | 无（重启重发） | 本地队列/会话 | 会话日志 + 团队日志（持久） |
| 可复用度 | 协议语义 | 交互模型 | **直接作为底座** |

## 5. 对本项目的结论

1. **调度不要自研**：DSH Agent Teams 已提供 roster、inbox、任务 DAG、CAS、投影、等待/中断；工作台只做"团队模板 + 派发 + 呈现"。
2. **页内会话的本质是"一个 Lead 会话的只读投影 + 输入通道"**，不是新聊天系统：读 `session/event` 渲染，写走 `sessions.prompt`。
3. **异常模型照 PixOffice + WorkBuddy 的组合**：把"已派发/执行中/已完成/失败/超时/取消"做成显式状态机；超时是终态；失败可重试但要保留证据。
4. **记忆必须分层**：个人（跨项目）/ 项目（随工作区）/ 团队（随团队模板），否则要么污染、要么丢失。
5. **知识系统先做 FTS5 全文 + 文件索引**，embedding 作为可选增强；不要一上来引入向量库。
6. **并发与超时得工作台自己管**：DSH Team 没有团队并发阀，也没有任务超时；并发靠 kickoff 与任务板 owner 数约束，超时靠工作台计时 + 中断/结束会话。
7. **运行中成员不可热改**：工具策略创建后不可变、名字不可复用；权限变更只对下次派发生效，或创建替代成员。
8. **PixOffice 不进入主链路**：已定 v1 不做 2D 可视化，只保留协议语义借鉴（团队/任务用卡片与状态点表达）。
9. **团队按功能服务，而不是按灵感手选**（v1.10 修正）：灵感页选团队会让用户为每次发散做重复决策；改为团队在配置里声明"哪个功能由哪些成员执行"，派发时按 feature 路由，主理人仍在运行期决定实际派谁。
10. **成员配置必须来自 DSH 真实目录**：手填 skills/mcp/tools 极易写错；v1.10 新增 `/agents/options` 聚合模型、技能、工具与 MCP 服务，前端只做选择。

> 详细可行性（逐项 API 证据、风险、spike 清单）见 `02-可行性评估.md`；产品形态、数据模型、流程与验收见 `03-产品设计.md`。
