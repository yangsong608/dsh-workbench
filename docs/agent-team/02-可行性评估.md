# 智能体团队 · 可行性评估

> 版本：v1（2026-10-23） · 对应需求见 `01-需求与技术分析.md`
> 结论先行：**需求 2/4/5/6 均可行，其中 5（页内会话 + 主理人调度）是唯一需要先做技术验证的高风险项；6（记忆/知识）工作量最大但风险最低。**

## 2. 逐项论证

### 2.1 需求 2：门户团队区块与自定义智能体

**结论：纯前端 + 本地数据，低风险。**

- 门户渲染已存在（`PORTAL_GROUPS` + 卡片 grid），在"功能区"下方加一个 `.portal-teams` 区块即可；
- 团队/成员存工作台 SQLite（`agent_teams`、`agent_members`），与灵感同库；
- 默认"产品研发团队"作为种子数据（主理人 + 产品/架构/前端/后端/测试/评审）；
- 自定义成员表单字段：名称、角色、系统提示、模型、可用工具集、技能、MCP、记忆范围；
- 模型列表从 DSH 模型目录读取（客户端已有类似能力，需确认 API：`ctx.get('models')` 或 session controller 的模型目录）。

**边界**：门户里的团队卡片是"模板/配置"态；只有派发过一次后才产生会话，才有 running 状态。UI 必须区分"模板"与"运行中"，否则用户会以为成员在后台一直工作。

**工作量**：2–3 人日。

---

### 2.2 需求 4：智能体使用 DSH Agent

**结论：可行，路径明确。**

- 创建会话：工作台客户端已用 `sessions.create({ workspaceId })` / `{ cwd }`（`createSessionIn`）；
- 发送：`sessions.retain` + `prompt`（或已绑定会话直接 prompt）；
- 模型：DSH 的 `modelSelection` 是 per-agent 的；**会话创建时能否指定模型需要 spike**（如果不支持，就在 kickoff 提示词里让 Lead 用 `model` 参数/或成员创建时的 provider 配置）；
- 团队：desktop profile 已装入 `@deepseek-ai/dsh-experimental-agent-team-profile`，会话内自动带 `agent_teams_*` 工具；本会话已验证这些工具存在；
- 团队服务 API：`ctx.agentTeams.spawnTeammate / createTask / updateTask / sendMessage / waitForChange / interrupt`，需要"确切的实时 Agent"作为调用凭证。

**风险**：实验性包，版本升级可能改 API。缓解：能力探测（`ctx.get('agentTeams')` 存在才用），核心链路保留"提示词驱动"降级。

**工作量**：1–2 人日（不含团队 UI）。

---

### 2.3 需求 5：页内会话 + 主理人调度（高风险）

这是整个需求的核心，拆成四个技术点：

#### (a) 在面板里拿到流式消息

**证据**：客户端插件可以订阅 `ctx.on('session/event', (session, event) => …)`（DSH 自带的 `file-upload`、`product-analytics` 都这么做）；`sessionController` 提供会话历史与实时状态的 Remote API。

**方案**：页内会话不自己造消息模型，而是"会话投影 + 增量渲染"：

```
sessions.create → sessionId
sessions.retain(sessionId) → 等待 ready
sessions.prompt(sessionId, kickoff)
ctx.on('session/event', …) → 过滤本 sessionId → 增量追加到面板
```

**风险**：事件体积大（含工具调用/推理块），需要节流 + 只渲染需要的块；Markdown 渲染要自带轻量实现（工作台不依赖官方 markdown 组件）。

**Spike S1**：在面板中跑通"创建会话 → 发送 → 流式渲染 3 条消息 → 断开重连后按历史补齐"。

#### (b) 拿到团队成员与任务状态

**证据**：Lead 会话把 `agentTeam` 投影发布给客户端（`SessionProjectionMap.agentTeam`：members + tasks + failure）；DSH 自带 `client-ui-agent-team` 就是渲染这个投影。

**方案**：优先读投影（最准）；读不到时降级为"解析工具调用事件"（`spawn_teammate`/`team_task_create` 的参数）本地还原。

**风险**：投影 API 是否对第三方客户端插件开放需要 spike；实验性。

**Spike S2**：在一个 session 上读到 `agentTeam.members` 与 `tasks`。

#### (c) 谁来决定团队怎么拆

**两条路**：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 提示词驱动 | 派发时给 Lead 一段结构化 kickoff（团队模板 + 任务 + 工具契约），由 Lead 调 `spawn_teammate` / `team_task_*` | 不改实验 API；贴近 DSH 设计 | 依赖模型遵守；需要校验 |
| B. 编程建队 | 工作台 host 用 `ctx.agents.create()` 拿 Lead 句柄，再 `ctx.agentTeams.spawnTeammate(lead, …)` 确定性建队 | 完全可控、可测试 | 强耦合实验 API；会话生命周期要自己管 |

**建议**：MVP 走 A，并在 kickoff 里写死"必须先建任务板、按成员职责创建 teammate、失败要发消息说明"；同时记录工具调用做校验（没建队就提示重试）。B 作为 **1.10** 的"确定性团队"增强。

**Spike S3**：A 路线在 3 个不同任务上验证 Lead 是否稳定按模板建出 **7 名成员（允许 ±1）**、任务板非空，并验证"并发 3"与"15 分钟超时"的两种控制手段（发消息 vs host 调用）是否都能落地；B 路线只做最小验证（创建 + spawn + 清理）。

#### (d) 成员能否调用工作台工具（把结果写回灵感）

**证据**：`ctx.tools.register` 注册的工具进入 profile 的工具集；团队模式下 `subagent`/`subagent_fork` 被禁用，但普通工具保留。

**方案**：`workbench_idea_expand` / `workbench_idea_progress` 保持全局注册，kickoff 里明确"由成员调用 `workbench_idea_expand` 写入节点，Lead 汇总后调 `workbench_idea_progress(done)`"。

**风险**：工具作用域若按 workspace 隔离，成员会话必须落在同一 workspace；需 spike 确认。

**Spike S4**：成员会话能否成功调用 `workbench_idea_expand` 并写库。

**工作量**：S1–S4 合计 3–4 人日；页内会话 UI 3 人日；团队/任务面板 2 人日。

### 2.4 需求 6：记忆与知识系统

**结论：可行，且是差异化能力。**

#### 记忆分层

| 层 | 作用域 | 存储 | 注入方式 |
|---|---|---|---|
| 个人记忆 | 跨项目、跨团队 | `<DSH_HOME>/dsh-workbench/memory/*.md` + DB 索引 | 派发前拼接进 kickoff 的 `<memory scope="personal">` |
| 项目记忆 | 随工作区 | `<workspace>/.dsh-workbench/memory.md` | 同上，scope="project"；可进 git 共享 |
| 团队记忆 | 随团队模板 | SQLite `team_memory` | 同上，scope="team" |
| 会话记忆 | 单次会话 | DSH session 日志 | 不重复注入，靠会话历史 |

写入时机：① 用户手动"记住这条"；② 会话结束由 Lead/成员调用 `workbench_memory_write`；③ 灵感采纳节点时自动摘要（可选）。

#### 知识系统

- **索引**：工作区文件（md/txt/docx 文本）、笔记、灵感图、Bug/测试记录、交付文档；
- **检索**：SQLite FTS5（`node:sqlite` 自带），BM25 排序 + 路径/类型过滤；
- **注入**：派发时对任务做一次检索，取 top-k（默认 6，约 3k tokens）注入 `<knowledge>` 段；
- **工具**：`workbench_knowledge_search` / `workbench_memory_search` 供成员按需再查；
- **可选增强**：embedding（本地或 provider）+ 混合排序；v1 不做。

**风险**：注入内容可能过期/冲突 → 每条知识带来源、时间、作用域，UI 可查看/删除；隐私 → 个人记忆默认不进项目仓库。

**Spike S5**：`node:sqlite` 的 FTS5 是否可用（`CREATE VIRTUAL TABLE … USING fts5`）；不可用则退化为 LIKE + 分词字段。

**工作量**：4–5 人日（含索引、注入、UI）。

## 3. 全局风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Agent Teams 是实验 API | 升级即坏 | 能力探测 + 适配层 + 降级为提示词驱动 |
| 成员并发写同一文件 | 冲突/覆盖 | 默认按角色限制（产品/测试/评审只读，前端/后端可写）；`writeScopes` 提示 + 按文件域拆任务；不承诺强一致 |
| 会话成本失控 | 费用/延迟 | 默认 7 成员但**团队并发 3（软约束：kickoff + 任务板 owner 数，DSH 无团队并发阀）**、任务上限、单次派发 token 预算、15 分钟超时终止 |
| 运行中改成员权限 | 无法热改 | DSH 工具策略创建后不可变、名字不可复用；只对下次派发生效，或创建替代成员（新名字）并中断旧成员 |
| 成员级工具策略不可用 | read 角色仍可能写文件 | 实验版 `spawn_teammate` 无 toolPolicy 字段；改用 `@nanmicoder/dsh-agent-teams` 的 `agent_teams_add_member(tool_policy)`，不可用则退化为 kickoff 约束 + DSH 审批 + 工具调用审计 |
| 团队并发无硬阀 | 7 人同时跑导致慢/贵 | 成员字段 `concurrency=1` + kickoff 限制同时 assign 3 个 in-progress；UI 显示当前 running 数并在超限时提示 |
| 页内会话事件量 | 卡顿 | 只渲染文本/工具摘要；虚拟列表；节流 50ms |
| 记忆污染 | 错误长期化 | 分层 + 来源 + 可删除 + 过期标记 |
| 工具越权 | 误改文件 | 复用 DSH 审批策略；高风险成员只给只读工具 |
| 多会话并发 | 资源 | 同一灵感同时只允许一个派发（互斥锁） |

## 4. Spike 清单（做设计评审后、正式开发前）

| ID | 验证内容 | 通过标准 | 预估 |
|---|---|---|---|

| S2 | 读取 `agentTeam` 投影 | 拿到 members + tasks，字段与文档一致 | 0.5d |

## 5. 分期与工作量

| 阶段 | 内容 | 人日 |
|---|---|---|
| P0 | 团队/成员数据模型（含 M:N 关联、fileWrite 预设、派发成员快照）、门户区块、默认 7 人产品研发团队、自定义成员 | 3.5 |
| P1 | 页内会话（创建/流式/停止/重试/历史） | 4 |
| P2 | 派发协议 + 主理人 kickoff + 团队成员/任务视图 + 异常态 | 4 |
| P3 | 记忆分层 + 知识索引 + 检索注入 + 设置 UI | 5 |
| P4 | 超时/重试/权限/成本护栏 + 自检 | 2 |
| 合计 | | **18.5 人日**（不含 Spike，约 4.75 人日含可选 S3b） |

**最小可用（MVP）**：P0 + P1 + P2 = 11.5 人日，先让"门户能看到 7 人团队、灵感右侧能开会话、主理人能派活"跑通，记忆放到下一版。

**已定决策对可行性的影响**：7 人 vs 5 人只增加配置与提示词长度，不改变架构；真正要控的是并发与预算（见风险表）。文件权限"运行时改"**不能热改**：要么只对下次派发生效，要么创建替代成员（DSH 名字不可复用），已在设计中写明，不影响可行性但会影响交互文案。

## 6. 明确不做（v1）

- 独立工作目录的成员（DSH Team 共享 cwd）；
- 跨进程成员（ACP/Codex/Claude Code 后端）——DSH 支持，但工作台不做配置面；
- 向量 RAG / 自动知识图谱；
- PixOffice 2D 办公室可视化（已定 v1 不做，只保留协议级借鉴）；
- 自动合并并发写冲突；
- 自动记忆提取（已定 v1 手动确认）；
- 运行中热改成员工具策略（DSH 不支持）；
- 团队级 RBAC/多租户。
